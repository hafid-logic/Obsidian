# S0 --- ملخص تنفيذي + أهم 5 قرارات + أكبر 3 مخاطر

[يبني هذا التصميم منصة تداول خوارزمي **منخفض الكمون (Low-Latency Quantitative Trading Platform --- المستوى L1: 5--50ms داخلياً)** مستقلة 100% عن Goldman Sachs Marquee وأي بنية مؤسسية مغلقة. **[قرار]**] **تصحيح التسمية إجباري**: النظام ليس HFT بالمعنى المؤسسي (L2: ميكروثانية/Colocation/FPGA)، بل نظام **Event-Driven Low-Latency Statistical & Microstructure Trading** يتنافس في أفق ثوانٍ إلى دقائق عبر نمذجة دقيقة لدفتر الأوامر (L2 Book)، طابور الأولوية (Queue Position)، وتكلفة الاختيار السلبي (Adverse Selection).

## أهم 5 قرارات معمارية:

**1.** **[قرار]** **بنية أحادية اللغة (Python 3.12+ مع** asyncio **+** uvloop **+** msgspec **+** numba**) في الحلقة الساخنة لـ L1، مع عزل التبعيات الثقيلة**: لمطوّر واحد وميزانية 50--500ms، تعقيد FFI بين Rust وPython في المرحلة الأولى يخلق عبء صيانة وتصحيح يفوق مكسب الميكروثانية. تُستخدم hftbacktest (المبنية على Rust/Numba) لمحاكاة الطابور (FR-303) دون بناء محرك C++/Rust من الصفر.

**2.** **[قرار]** **تمثيل الأسعار والكميات بأعداد صحيحة قياسية 64-بت (**Scaled Int64 **--- Fixed-Point Arithmetic)**: يُمنع float64 (لأخطاء التقريب الثنائي في مطابقة مستويات السعر) ويُمنع Decimal في الحلقة الساخنة (للبطء وضغط الذاكرة). السعر والكمية يُخزنان كـ int64 مضروبين في معامل قياس ثابت (10^8 أو حسب tick_size/lot_size).

**3.** **[قرار]** **ناقل أحداث داخل العملية (In-Process Single-Threaded Event Loop + Ring Buffer) مع سجل أحداث ثنائي (Append-Only Binary WAL)**: تحقيق حتمية كاملة (Deterministic Replay --- FR-307) واستغناء تام عن Redis في الملف الأدنى (Minimal Profile 1GB RAM).

**4.** **[قرار]** **اعتماد Bybit / OKX / Kraken + Hyperliquid (DEX L1) كبدائل معيارية عبر** BrokerAdapter **بدلاً من افتراض Binance**: نظراً للحظر الجغرافي وقيود KYC في Binance **[UNVERIFIED]**.

**5.** **[قرار]** **بوابة مخاطر دالية نقية (Pure Synchronous Pre-Trade Risk Gate) بوضع Fail-Closed**: تعمل في نفس الحلقة الحدثية قبل أي استدعاء شبكي، بزمن تنفيذ \< 50µs، ولا يمكن لأي وكيل خارجي (FR-703) أو استراتيجية تخطيها.

## أكبر 3 مخاطر وجودية:

**1.** **وهم ربحية صانع السوق (Market Making Adverse Selection)**: في بنية مجانية عبر إنترنت عام (RTT 30--150ms)، أوامر post-only تُلتقط بواسطة متداولين أسرع عند تغير السعر اللحظي (Pick-off Risk) قبل وصول طلب الإلغاء.

**2.** **انجراف حالة دفتر الأوامر المحلي (Silent L2 Book Corruption)**: فقدان حزمة diff واحدة في WebSocket دون آلية تحقق صارمة من sequence_id يؤدي إلى التسعير على دفتر وهمي وخسائر فورية.

**3.** **الانحياز الإحصائي في الاختبار الرجعي (Backtest Overfitting & Queue Optimism)**: افتراض التعبئة الفورية عند لمس السعر (Touch-is-Fill) يضخم العوائد النظرية بـ 300%--500% مقارنة بالواقع.

## 5.2 مسارات الفشل الأربعة الحرجة (Failure Paths)

**1.** **مسار انقطاع البيانات (WebSocket Disconnect / Silent Stall)**:

**•** HeartbeatMonitor يكتشف غياب أي رسالة لـ > 3,000ms.
**•** يصدر حدث MarketDataStaleEvent إلى الـ Bus ← تنتقل حالة السوق إلى HALTED_STALE.
**•** RiskGate ترفض فوراً أي OrderIntent جديد (باستثناء أوامر Cancel أو Reduce-Only الطارئة).
**•** OMS يلغي جميع أوامر صانع السوق المفتوحة (CancelAllMakerOrders) عبر REST لمنع Adverse Selection أثناء العمى.
**•** WSConnector يعيد الاتصال تراجعياً، يجلب Snapshot جديداً للدفتر وBackfill للشموع، ولا يعود النظام إلى ACTIVE إلا بعد نجاح L2ChecksumVerifier.

**2.** **مسار تكرار الرسائل أو إعادة إرسال الأوامر (Duplicate Events / Network Timeout)**:

**•** كل حدث سوق يحمل seq_id؛ أي حدث بـ seq_id \<= last_processed_seq_id يُسقط صامتاً في Normalizer.
**•** عند انتهاء مهلة إرسال أمر (HTTP Timeout)، ينتقل الأمر في OMS إلى UNKNOWN_IN_FLIGHT (وليس REJECTED).
**•** يقوم OrderReconciler بالاستعلام عن الأمر بواسطة client_order_id الحتمي قبل اتخاذ أي قرار بإعادة الإرسال، مما يمنع التنفيذ المزدوج 100%.

**3.** **مسار تلف دفتر الأوامر المحلي (Corrupted L2 Order Book --- FR-107)**:

**•** إذا وصل تحديث U حيث U.first_update_id > book.last_update_id + 1، أو فشل تحقق CRC32 Checksum:
**•** يُوسم الدفتر فوراً بـ BookState.CORRUPTED ← تُلغى الأوامر المعلقة على هذا الزوج ← يُطلب Snapshot جديد من REST مع تجميع التحديثات في Buffer مؤقت حتى تكتمل المزامنة.

**4.** **مسار التأخر الداخلي وانجراف الساعة (High Latency / Clock Skew / GC Spike)**:

**•** إذا تجاوز الكمون الداخلي t4 - t1 > 25ms أو انحراف الساعة |clock_skew| > 250ms:
**•** ترفض RiskGate الأمر لأن السعر الذي بُني عليه القرار أصبح قديماً (Stale Quote Protection).

self._max_market_queue = max_market_queue

def publish_priority(self, event: Any) -> None:
self._priority_queue.append(event)
def publish_market(self, event: Any) -> None:
if len(self._market_queue) >= self._max_market_queue:
self._market_queue.popleft() # Drop oldest stale tick on extreme backpressure
self.dropped_market_events += 1
self._market_queue.append(event)
def drain_all(self) -> int:
processed = 0
while self._priority_queue or self._market_queue:
# Priority events (Fills, Rejects, KillSwitch) ALWAYS execute before new Market ticks
ev = self._priority_queue.popleft() if self._priority_queue else self._market_queue.popleft()
for handler in self._subscribers.get(type(ev), ()):
handler(ev)
processed += 1
return processed

## المستوى A --- البند 9 و 10: تكافؤ Backtest/Live وواجهة نموذج الطابور القابلة للتبديل (Queue Fill Simulator --- FR-303)

**•** **اللغة**: Python 3.12 **[غير مشغّل]**

**•** **آلية التكافؤ (البند 9)**: TradingKernel يأخذ (Clock, EventBus, StrategyPlugin, RiskLimits, BrokerAdapter). في Live نمرر (LiveClock, LiveExchangeBroker)؛ وفي Backtest نمرر (SimulatedClock, QueueSimulatorBroker) دون تغيير سطر واحد في TradingKernel.

**•** **نموذج الطابور المحافظ (البند 10)**: عندما يدخل أمر Limit عند سعر $P*، نسجل حجم السيولة المعروضة أمامه في الدفتر \`queue*~a~*head*~q~*ty\`. لا يُملأ الأمر عند *P$ إلا إذا حدثت صفقات بيع/شراء عند $P *تتجاوز \`queue*~a~*head*~q~*ty\`، أو اخترق السعر المستوى *P$ كلياً. وعند انخفاض حجم المستوى في L2 (إلغاءات)، نفترض محافظين أن الإلغاءات حدثت **خلفنا** في الطابور (أو بنسبة محافظة alpha = 0.2).

# [غير مشغّل] - المستوى A (البند 9 + البند 10): Queue Position Fill Model & Parity Wiring
import msgspec
class SimulatedRestingOrder(msgspec.Struct):
cmd: ApprovedOrderCommand
remaining_qty_scaled: int
queue_ahead_qty_scaled: int # Quantity ahead of us at the same price level
active_from_ts_ns: int # Simulated arrival time (signal_ts_ns + simulated_latency_ns)
class QueueFillModel:
def __init__(self, entry_latency_ns: int = 35_000_000, cancel_decay_factor: float = 0.25) -> None:
self.entry_latency_ns = entry_latency_ns
self.cancel_decay_factor = cancel_decay_factor
def on_order_placed(self, cmd: ApprovedOrderCommand, book: L2BookEvent) -> SimulatedRestingOrder | None:
p = cmd.intent.limit_price_scaled or 0
# Post-only check: if order crosses the book on arrival, reject immediately
if cmd.intent.order_type == OrderType.POST_ONLY:
if (cmd.intent.side == Side.BUY and book.asks and p >= book.asks[0].price_scaled) or \
(cmd.intent.side == Side.SELL and book.bids and p \<= book.bids[0].price_scaled):
return None # Rejected by post-only rule
levels = book.bids if cmd.intent.side == Side.BUY else book.asks
ahead = next((lvl.qty_scaled for lvl in levels if lvl.price_scaled == p), 0)
return SimulatedRestingOrder(
cmd=cmd,
remaining_qty_scaled=cmd.intent.qty_scaled,
queue_ahead_qty_scaled=ahead,
active_from_ts_ns=cmd.risk_approved_ts_ns + self.entry_latency_ns,
)
def on_trade(self, order: SimulatedRestingOrder, trade: TradeEvent) -> int:
if trade.exchange_ts_ns \< order.active_from_ts_ns:
return 0
p = order.cmd.intent.limit_price_scaled or 0
side = order.cmd.intent.side
# Case 1: Price strictly traded through our limit price -> Full fill
if (side == Side.BUY and trade.price_scaled \< p) or (side == Side.SELL and trade.price_scaled > p):
filled = order.remaining_qty_scaled
order.remaining_qty_scaled = 0
return filled
# Case 2: Trade occurred exactly at our limit price -> Deplete queue ahead first
if trade.price_scaled == p:
if order.queue_ahead_qty_scaled >= trade.qty_scaled:
order.queue_ahead_qty_scaled -= trade.qty_scaled
return 0
leftover = trade.qty_scaled - order.queue_ahead_qty_scaled
order.queue_ahead_qty_scaled = 0
filled = min(order.remaining_qty_scaled, leftover)
order.remaining_qty_scaled -= filled
return filled
return 0

## المستوى A --- البند 11: بروتوكول الاستمرارية (Binary WAL) والمطابقة عند الإقلاع (Recovery & Reconciler --- FR-404 / NFR-202)

# [غير مشغّل] - المستوى A (البند 11): Binary WAL with CRC32 & Startup Reconciler
import struct
import zlib
import msgspec
class BinaryWAL:
# Frame layout: [uint32 length][uint32 crc32][uint8 event_tag][bytes msgpack_payload]
HEADER_STRUCT = struct.Struct("\<IIB")
def __init__(self, file_path: str) -> None:
self._fp = open(file_path, "ab+", buffering=0)
def append(self, event_tag: int, obj: msgspec.Struct) -> None:
payload = msgspec.msgpack.encode(obj)
crc = zlib.crc32(payload) & 0xFFFFFFFF
header = self.HEADER_STRUCT.pack(len(payload), crc, event_tag)
self._fp.write(header + payload)
def replay(self):
self._fp.seek(0)
while header_bytes := self._fp.read(self.HEADER_STRUCT.size):
if len(header_bytes) \< self.HEADER_STRUCT.size:
break # Truncated tail frame on power loss -> safely stop
length, expected_crc, tag = self.HEADER_STRUCT.unpack(header_bytes)
payload = self._fp.read(length)
if len(payload) \< length or (zlib.crc32(payload) & 0xFFFFFFFF) != expected_crc:
raise RuntimeError("WAL_CORRUPTION_DETECTED: CRC mismatch")
yield tag, payload
async def reconcile_on_startup(broker: BrokerAdapter, local_open_ids: set[str], local_pos: dict[str, int]) -> bool:
remote_orders = await broker.fetch_open_orders()
remote_ids = {o["client_order_id"] for o in remote_orders}
remote_pos = await broker.fetch_positions()
if remote_ids != local_open_ids or remote_pos != local_pos:
# Cancel any orphan orders on exchange and block trading until resolved
await broker.cancel_all_orders()
return False
return True

## 8.2 نقد مرجعية Haim Bodek (ما ينتقل إلى الكريبتو وما لا ينتقل)

**•** **ما لا ينتقل من أطروحة Bodek الأصلية**:

أطروحة Bodek (في كتابه *The Problem of HFT* وشكوى SEC ضد Direct Edge/BATS) تركزت حول **التعقيد التنظيمي لنظام NMS الأمريكي (Reg NMS Rule 611 --- Order Protection Rule)**، حيث اضطرت البورصات لابتكار أنواع أوامر معقدة وغير موثقة للعامة (مثل *Hide Not Slide*) لتجنب قفل السوق (Locked/Crossed Markets)، واستغل المتداولون المطلعون هذا التفاوت الهندسي لتخطي طابور المتداولين العاديين. **في الكريبتو، لا يوجد Reg NMS ولا حظر قانوني لتقاطع الأسعار بين البورصات، ومحركات المطابقة أبسط بكثير (FIFO Price-Time Priority معلنة).**

**•** **ما ينتقل بقوة ويشكّل عصب تصميمنا**:

**1.** **حتمية أنواع الأوامر (**Post-Only **/** IOC**)**: إن لم تستخدم Post-Only لصناعة السوق، فإن تأخر الشبكة بـ 50ms سيحول أمرك من Maker إلى Taker (عبور السبريد) ويدمر اقتصاديات الاستراتيجية فوراً بسبب فرق الرسوم.
**2.** **الاختيار السلبي (Adverse Selection --- Glosten & Milgrom 1985 / Kyle 1985)**: في الكريبتو، عندما يُملأ أمر Post-Only الخاص بك على خادم مجاني (كمون 80ms)، فهناك احتمال مرتفع أن صانع سوق مؤسسياً (كمون 2ms) قد رأى حركة سعرية على منصة أخرى والتقط أمرك قبل أن يصل طلب الإلغاء الخاص بك.
**3.** **قابلية التفسير الجنائي لكل صفقة (Forensic Explainability)**: تسجيل حالة الدفتر وموقع الطابور لحظة إرسال الأمر ولحظة التعبئة لمعرفة هل ربحنا من السبريد أم خسرنا بسبب الاختيار السلبي.

## 10.2 سجل القرارات المعمارية (Architecture Decision Records --- ADR)

### ADR-001: اختيار Python 3.12 (uvloop + msgspec + numba) بدلاً من Rust الكاملة أو الهجينة للمرحلة الأولى

**•** **السياق**: نحتاج زمن معالجة داخلي \< 10ms (NFR-201) مع قدرة مطوّر واحد على بناء النظام، اختباره، وتشغيله في Paper خلال أسبوع واحد (T4).

**•** **القرار**: [**[قرار]** استخدام Python 3.12+ أحادية الخيط الحدثي مع] msgspec للترميز وnumba للمؤشرات.

**•** **البدائل المرفوضة**:

**•** *Rust كاملة*: تبطئ تطوير الاستراتيجيات والتحليل الإحصائي بشكل كبير.
**•** *Hybrid Python+Rust منذ اليوم الأول*: تخلق عبء بناء (maturin) وتصحيح أخطاء عبر حدود FFI لا مبرر له طالما كمون الشبكة المجانية هو 30--150ms.

**•** **العواقب**: إنجاز سريع جداً وتكافؤ 100% بين الكود البحثي والحي؛ يتطلب الانضباط في عدم إنشاء كائنات ضخمة داخل الحلقة الساخنة لتفادي GC pauses.

### ADR-002: تمثيل الأسعار والكميات بـ ScaledInt64 (Fixed-Point *10^8*)

**•** **السياق**: الأرقام العشرية الثنائية (float64) تسبب أخطاء مقارنة في مفاتيح أسعار دفتر الأوامر، وdecimal.Decimal في Python بطيء ويستهلك ذاكرة عالية.

**•** **القرار**: [**[قرار]** تحويل جميع الأسعار والكميات عند حدود الإدخال (]Normalizer) إلى أعداد صحيحة int64 مضروبة في *10^8*.

**•** **البدائل المرفوضة**: float64 (خطر عدم تطابق مستويات السعر في L2)، Decimal (بطيء بـ 30x).

**•** **العواقب**: عمليات جمع وطرح ومقارنة فورية على مستوى المعالج ودقة مطلقة؛ يتطلب دوال مساعدة واضحة عند الضرب والقسمة ((a * b) // PRICE_SCALE).

### ADR-003: الاستغناء عن Redis واعتماد ناقل أحداث داخل العملية + Binary WAL + SQLite WAL

**•** **السياق**: الخوادم السحابية المجانية الدائمة (مثل GCP e2-micro أو VPS صغير) تملك 1GB RAM فقط (NFR-207).

**•** **القرار**: [**[قرار]** تشغيل ناقل الأحداث داخل العملية (In-Process) مع التسجيل الفوري في ملف] Binary WAL محلي وقاعدة SQLite WAL لحالة الأوامر.

**•** **البدائل المرفوضة**: Redis Streams / Kafka (استهلاك ذاكرة مرتفع، وكمون تسلسل عبر الشبكة المحلية، وتعقيد في إعادة التشغيل الحتمي).

**•** **العواقب**: استهلاك ذاكرة إجمالي \< 400MB، كمون ناقل \< 5µs، وإعادة تشغيل حتمية بالبت (FR-307).

### ADR-004: تصميم بوابة المخاطر كدالة نقية متزامنة بوضع الإغلاق الآمن (Fail-Closed Pure RiskGate)

**•** **السياق**: أي خطأ برمجي أو تأخر في بيانات السوق قد يؤدي لإرسال أوامر كارثية.

**•** **القرار**: [**[قرار]** تنفيذ] evaluate_pre_trade_risk كدالة نقية خالية من I/O، محاطة بـ try/except شامل يُرجع False عند أي استثناء أو نقص في البيانات.

**•** **البدائل المرفوضة**: فحص المخاطر غير المتزامن أو المعتمد على استعلامات خارجية وقت الأمر.

**•** **العواقب**: حماية مطلقة لرأس المال بزمن تنفيذ \< 50µs؛ قد تُرفض بعض الأوامر الصالحة لحظة تذبذب اتصال WebSocket، وهو سلوك مقصود وآمن (Control over Speed).

### ADR-005: عزل واجهة التحكم الخارجية (FR-703) بنموذج الأوامر الموقعة الثابتة

**•** **السياق**: ربط وكلاء الذكاء الاصطناعي أو البوتات الخارجية يفتح ثغرة Prompt Injection.

**•** **القرار**: [**[قرار]** قصر واجهة التحكم الخارجية على 4 أوامر enum ثابتة وموقعة بـ HMAC (]PAUSE, RESUME, ENGAGE_KILL_SWITCH, APPLY_SIGNED_PRESET)، ومنع تمرير أي معاملات رقمية أو رموز أسهم/عملات أو تعديل حدود المخاطر.

**•** **البدائل المرفوضة**: السماح للوكيل الخارجي بإرسال OrderIntent أو تعديل RiskLimits.

**•** **العواقب**: حتى لو اختُرق وكيل الذكاء الاصطناعي بالكامل، أقصى ما يمكنه فعله هو إيقاف التداول أو التبديل بين إعدادين محافظين معتمدين مسبقاً من المالك.

# S0: الملخص التنفيذي + أهم 5 قرارات + أكبر 3 مخاطر

يبني هذا التصميم منصة تداول خوارزمي **متوسطة/منخفضة الكمون (L1: 50--500ms)** مستقلة 100% عن gs-quant وGS Marquee[، وتعمل بالكامل ضمن أدوات مفتوحة المصدر وطبقات مجانية دائمة. يُصحح التصميم تسمية "HFT" إلى **"تداول خوارزمي مبني على الأحداث (Event-Driven Algorithmic Trading - L1)"** لأن الكمون الميكروثاني (L2) مستحيل فيزيائياً وتشغيلياً عبر الإنترنت العام والخوادم المجانية **[قرار]**].

## أهم 5 قرارات معمارية:

**1.** **[قرار] بنية هجينة (Python 3.12 + Rust عبر PyO3/NautilusTrader أو محرك Event-Driven مدمج بـ]** uvloop **+** msgspec **+** numba**)**: كتابة عقود النظام ومنطق الاستراتيجيات بـ Python (لتسريع إنتاجية المطور الوحيد وإنجاز المرحلة 1 في أسبوع)، مع الاعتماد على هياكل بيانات ثابتة وأعداد صحيحة مقياسية (Fixed-Point i64) في المسار الساخن، واستخدام hftbacktest / NautilusTrader للمحاكاة الدقيقة لدفتر الأوامر **[UNVERIFIED]**.

**2.** **[قرار] تمثيل الأسعار والكميات والأزمان بأعداد صحيحة 64-بت (]**i64**)**: حظر float (IEEE 754) وDecimal البطيء في الحلقة الساخنة؛ تُخزَّن الأسعار والكميات بمقياس ثابت (SCALE = 10^8) والأزمان بالنانوثانية (int64 epoch ns) لضمان الحتمية الحسابية (FR-307) وسرعة المعالجة.

**3.** **[قرار] ناقل أحداث داخل العملية (In-Process Ring Buffer / Asyncio Queue) مع سجل WAL ثنائي (]**Parquet **+** SQLite WAL**)**: استبعاد Redis وKafka في الملف الأدنى (Minimal Profile) توفيراً للذاكرة (RAM ≤ 1GB) والكمون الداخلي، مع كتابة غير حاجزة (non-blocking) إلى قرص محلي بصيغة Arrow/Parquet للتشغيل الرجعي الحتمي.

**4.** **[قرار] بوابة مخاطر نقية حتمية (]**Fail-Closed RiskGate**) مفصولة قبل الـ OMS**: أي غموض في حالة الرصيد، أو انجراف ساعة يتجاوز 250ms، أو فجوة في sequence_id لدفتر الأوامر المحلي (L2 Book) يوقف إصدار الأوامر فوراً (Kill Switch) ولا يسمح إلا بأوامر الإلغاء أو الإغلاق (reduce-only).

**5.** [**[قرار] تكافؤ تام بين Backtest وPaper وLive (Single-Codebase Parity)**: تشترك المسارات الثلاثة في كود] StrategyPlugin وRiskGate وOrderStateMachine وFeatureEngine بالبت؛ ويتغير فقط Clock وDataSource وExecutionSink.

## أكبر 3 مخاطر:

**1.** **الاختيار السلبي (Adverse Selection) وتآكل الربحية بالرسوم**: في الكريبتو، صناع السوق المحترفون يتمتعون باتصال مباشر ورسوم صفرية/سلبية (VIP Tiers)، بينما حساب التجزئة المجاني يدفع 2--10 bps **[UNVERIFIED]** ويُملأ أمره غالباً عندما يتحرك السعر ضده.

**2.** **فقدان المزامنة أو تلف دفتر الأوامر المحلي (Silent L2 Book Corruption)**: فقدان رسالة WebSocket واحدة دون كشف فجوة update_id يؤدي إلى التسعير على أفضل عرض/طلب وهمي (crossed/stale book).

**3.** **الانجراف الخفي في الإعدادات أو فرط التخصيص (Backtest Overfitting)**: غياب Deflated Sharpe Ratio وPurged Walk-Forward يجعل الاستراتيجيات تبدو رابحة تاريخياً بينما هي خاسرة حتمياً في السوق الحي.

## 5.2 مسارات الفشل الأربعة الحرجة (Failure Paths)

**1.** **مسار انقطاع الاتصال (Connection Drop)**:

**•** عند سقوط WebSocket، يطلق WSClient حدث ChannelDisconnected فوراً إلى RiskGate فتتحول حالة النظام إلى DEGRADED_HALT_NEW_ORDERS خلال \< 1ms.
**•** يبدأ الاتصال التراجعي (Exponential Backoff: 0.5s, 1s, 2s, 4s\... max 30s + jitter).
**•** بعد عودة الاتصال: يُشغَّل StartupReconciler لمطابقة الأوامر المفتوحة، ثم يُطلب REST L2 Snapshot جديد وتُفرغ فجوة الشموع عبر REST قبل رفع الحظر عن الاستراتيجية.

**2.** **مسار التكرار ومنع الأمر المزدوج (Duplicate Events & Order Idempotency)**:

**•** رسائل السوق المكررة (seq_id \<= last_processed_seq_id) تُسقط بصمت في BookMaintainer.
**•** عند انقطاع الشبكة أثناء إرسال أمر (HTTP Timeout حيث لا نعلم هل وصل الأمر للبورصة أم لا)، ينتقل الأمر في OMS إلى حالة PENDING_RECONCILE (وليس REJECTED). يستعلم الـ OMS عن الأمر باستخدام نفس client_order_id الحتمي؛ فإن وجده مفتوحاً اعتمد حالته، وإن لم يجده أعاد إرساله بنفس client_order_id لمنع التنفيذ المزدوج (FR-406).

**3.** **مسار التأخر والبيانات القديمة (Stale Data & High Latency)**:

**•** يفحص RiskGate شرطين زمنيين لكل أمر جديد: (أ) now_ns - last_book_update_ingest_ns \< max_staleness_ns (افتراضياً 2,000ms للكريبتو)، و(ب) ingest_ts_ns - exchange_ts_ns \< max_feed_delay_ns (افتراضياً 500ms). إذا خُرق أي منهما (بسبب تجميد GC أو ازدحام الشبكة)، يُرفض الأمر فوراً بوسم REJECT_STALE_MARKET_DATA.

**4.** **مسار تلف دفتر الأوامر المحلي (Corrupted L2 Book)**:

**•** يُعتبر الدفتر تالفاً في 3 حالات: (أ) فجوة في seq_id، (ب) best_bid >= best_ask (Crossed Book)، (ج) فشل مطابقة CRC32 Checksum الدوري مع البورصة.

# [غير مشغّل] A.4: Deterministic Event Bus with Back-Pressure Contract
from collections import deque
from typing import Callable, Any
class BackPressureError(RuntimeError):
"""يُطلق عندما تتجاوز قائمة الانتظار السعة القصوى لمنع التداول على بيانات متأخرة."""
class DeterministicEventBus:
def __init__(self, max_queue_size: int = 10_000) -> None:
self._queue: deque[Any] = deque()
self._max_size = max_queue_size
self._subscribers: dict[type, list[`Callable[[Any], None]]]` = {}
self._seq_counter: int = 0
def subscribe(self, event_type: type, handler: `Callable[[Any], None])` -> None:
self._subscribers.setdefault(event_type, []).append(handler)
def publish(self, event: Any) -> int:
if len(self._queue) >= self._max_size:
raise BackPressureError(f"EventBus overflow: {len(self._queue)} >= {self._max_size}")
self._seq_counter += 1
self._queue.append(event)
return self._seq_counter
def drain_all(self) -> int:
processed = 0
while self._queue:
ev = self._queue.popleft()
for handler in self._subscribers.get(type(ev), ()):
handler(ev)
processed += 1
return processed

return f"A{intent_seq:09d}{digest}" # مثال: A000000042f9a1c3e8\...
def transition_order(current: OrderStatus, target: OrderStatus) -> OrderStatus:
if target not in VALID_TRANSITIONS[current]:
raise ValueError(f"Illegal OMS transition: {current} -> {target}")
return target

max_order_notional_fp: int
max_position_notional_fp: int
max_daily_loss_fp: int
max_orders_per_min: int
max_price_collar_bps: int # مثال: 100 = 1.00% انحراف أقصى عن Mid
max_book_staleness_ns: int # مثال: 2_000_000_000 (2s)
max_clock_drift_ns: int # مثال: 250_000_000 (250ms)
class RiskStateSnapshot(msgspec.Struct, frozen=True):
kill_switch_active: bool
book_is_valid: bool
now_ns: int
last_book_ingest_ns: int
abs_clock_drift_ns: int
mid_price_fp: int
current_pos_qty_fp: int
daily_total_pnl_fp: int # Realized + Unrealized
orders_last_60s: int
def evaluate_risk_gate(intent: "OrderIntent", state: RiskStateSnapshot, lim: RiskLimits) -> tuple[bool, str]:
try:
if state.kill_switch_active:
return False, "REJECT_KILL_SWITCH_ACTIVE"
if not state.book_is_valid or state.mid_price_fp \<= 0:
return False, "REJECT_BOOK_INVALID_OR_EMPTY"
if (state.now_ns - state.last_book_ingest_ns) > lim.max_book_staleness_ns:
return False, "REJECT_STALE_BOOK"
if state.abs_clock_drift_ns > lim.max_clock_drift_ns:
return False, "REJECT_CLOCK_DRIFT_EXCEEDED"
if state.daily_total_pnl_fp \<= -lim.max_daily_loss_fp and not intent.reduce_only:
return False, "REJECT_DAILY_LOSS_LIMIT"
if state.orders_last_60s >= lim.max_orders_per_min:
return False, "REJECT_ORDER_RATE_LIMIT"
ref_px = intent.limit_price_fp or state.mid_price_fp
if abs(ref_px - state.mid_price_fp) * 10_000 > state.mid_price_fp * lim.max_price_collar_bps:
return False, "REJECT_PRICE_COLLAR"
notional_fp = (intent.qty_fp * ref_px) // 100_000_000
if notional_fp > lim.max_order_notional_fp and not intent.reduce_only:
return False, "REJECT_MAX_ORDER_NOTIONAL"
new_pos_qty = state.current_pos_qty_fp + (intent.side * intent.qty_fp)
new_pos_notional = (abs(new_pos_qty) * state.mid_price_fp) // 100_000_000
if new_pos_notional > lim.max_position_notional_fp and not intent.reduce_only:
return False, "REJECT_MAX_POSITION_NOTIONAL"
return True, "APPROVED"
except Exception:
return False, "REJECT_FAIL_CLOSED_EXCEPTION"

import msgspec
class SimulatedQueueOrder(msgspec.Struct):
client_order_id: str
side: int # 1=BUY, -1=SELL
limit_price_fp: int
remaining_qty_fp: int
queue_ahead_fp: int # الكمية التي تسبقنا في نفس مستوى السعر
active_after_ns: int # وقت وصول الأمر للبورصة (ingest_ts_ns + latency_ns)
class ConservativeL2QueueFillModel:
def on_market_trade(self, order: SimulatedQueueOrder, tick: "MarketTickEvent") -> int:
if tick.exchange_ts_ns \< order.active_after_ns or order.remaining_qty_fp \<= 0:
return 0
# 1. Trade-through: السعر تجاوز سعر أمرنا بالكامل
if (order.side == 1 and tick.price_fp \< order.limit_price_fp) or (
order.side == -1 and tick.price_fp > order.limit_price_fp
):
filled = order.remaining_qty_fp
order.remaining_qty_fp = 0
order.queue_ahead_fp = 0
return filled
# 2. Trade at our exact price level: استنفاد الطابور الذي أمامنا أولاً
if tick.price_fp == order.limit_price_fp:
consumed_ahead = min(order.queue_ahead_fp, tick.qty_fp)
order.queue_ahead_fp -= consumed_ahead
leftover_trade = tick.qty_fp - consumed_ahead
filled = min(order.remaining_qty_fp, leftover_trade)
order.remaining_qty_fp -= filled
return filled
return 0

## [8.2 نقد مرجعية Haim Bodek --- ما ينتقل للكريبتو وما لا ينتقل (**[قرار]**])

**•** **ما لا ينتقل (خاص ببورصات الأسهم الأمريكية 2008--2012 وReg NMS)**:

**•** أطروحة Bodek المركزية في كتابه *"The Problem of HFT"* وشكواه ضد BATS/Direct Edge دارت حول **أنواع أوامر معقدة وغير موثقة بشفافية** (Hide Not Slide، إلخ) صُممت للتعامل مع قاعدة حظر قفل السوق (Rule 610 Lock/Cross Market Prohibition في Reg NMS) ومنح أفضلية خفية في الطابور عند فك القفل **[UNVERIFIED]**.
**•** في سوق الكريبتو، **لا يوجد Reg NMS ولا يوجد NBBO موحد قانونياً بين البورصات**، ومحركات المطابقة داخل كل بورصة تستخدم خوارزمية Price-Time Priority (FIFO) معلنة وبسيطة نسبياً (أوامر Market, Limit, Post-Only, IOC, FOK). لذا فإن استدعاء Bodek للحديث عن "أنواع أوامر سرية" في الكريبتو هو **زخرفة غير علمية نرفضها**.

**•** **ما ينتقل فعلاً وبقوة إلى تصميمنا**:

**1.** Post-Only **وحماية الرسوم**: إذا أرسلت أمر Limit عادي وتحرك السعر لحظة وصول أمرك، سيُنفذ كـ Taker وتدفع رسوماً مضاعفة تقضي على هامش الصفقة. استخدام Post-Only إلزامي لأي استراتيجية تعتمد على رسوم الـ Maker.
**2.** **موقع الطابور (**Queue Priority**) والاختيار السلبي (**Adverse Selection **- Glosten & Milgrom 1985)**: عندما تكون في آخر الطابور عند أفضل سعر شراء (Best Bid)، فإن الصفقة الوحيدة التي ستملأ أمرك بالكامل هي بيع عدواني كبير يطيح بالسعر للأسفل (تُملأ في الخاسر وتفوتك التعبئة في الرابح).
**3.** **الشفافية الجنائية (**Forensic Explainability**)**: مبدأ Bodek في تسجيل سبب كل قرار وحالة دفتر الأوامر لحظة الإرسال (NFR-208) هو خط الدفاع الوحيد لاكتشاف الخلل البرمجي أو الاختيار السلبي.

## 8.3 حكم الجدوى الصادق للاستراتيجيات المرجعية الثلاث (FR-702 Viability Verdict)

## 10.2 سجل قرارات المعمارية (Architecture Decision Records --- ADR)

### ADR-001: استبدال الأعداد العشرية/العائمة بـ Fixed-Point i64 في المسار الساخن

**•** **السياق**: الأعداد العائمة (float64) تسبب أخطاء تقريب تراكمية (0.1 + 0.2 != 0.3) تكسر شروط أسعار البورصة (Tick Size) وتخل بالحتمية (FR-307)؛ بينما decimal.Decimal في Python أبطأ بـ 10--30 مرة وتخصص كائنات في الذاكرة.

**•** **[القرار ([قرار])**: تمثيل كافة الأسعار والكميات وقيم PnL في النواة كأعداد صحيحة 64-بت مضروبة في *10^8* (PRICE_SCALE = 100_000_000).

**•** **البدائل المرفوضة**: float64 (غير حتمي عبر المعالجات)، decimal.Decimal (بطيء ويسبب ضغطاً على GC).

**•** **العواقب**: عمليات جمع وطرح ومقارنة في أجزاء من النانوثانية وحتمية 100%؛ يتطلب دالة تحويل عند حافة البورصة (to_fixed / from_fixed).

### ADR-002: حلقة أحداث أحادية الخيط (Single-Threaded Event Loop) بدلاً من تعدد الخيوط والأقفال

**•** **السياق**: استخدام خيوط متعددة (Threads) تتشارك حالة دفتر الأوامر والـ OMS يتطلب أقفالاً (Locks/Mutexes) ترفع الكمون، وتخلق حالات سباق (Race Conditions)، وتجعل إعادة التشغيل الحتمية (FR-307) شبه مستحيلة.

**•** **[القرار ([قرار])**: معالجة كافة الأحداث (MarketEvent -> FeatureEngine -> Strategy -> RiskGate -> OMS) تسلسلياً في خيط واحد حتمي، مع فصل القراءة/الكتابة الشبكية والقرصية في مهام I/O غير حاجزة.

**•** **البدائل المرفوضة**: بنية متعددة الخيوط بأقفال؛ أو نشر Redis Streams بين حاويات متعددة على خادم 1GB RAM.

**•** **العواقب**: ضمان ترتيب أحداث حتمي 100%، استهلاك ذاكرة \< 50MB للنواة، وسهولة تصحيح الأخطاء.

### ADR-003: ثلاثية التخزين المدمجة (Parquet + DuckDB + SQLite WAL) بدلاً من قواعد البيانات الخادمية

**•** **السياق**: يتطلب النظام تسجيل ملايين أحداث السوق (FR-106) وحفظ حالة الأوامر بموثوقية (NFR-202) ضمن ميزانية موارد تبدأ من 1 vCPU / 1GB RAM (NFR-207).

**•** **[القرار ([قرار])**: استخدام Parquet (zstd) للأحداث الزمنية، DuckDB للاستعلام التحليلي، وSQLite WAL لحالة الـ OMS.

**•** **البدائل المرفوضة**: ClickHouse / QuestDB / PostgreSQL / TimescaleDB (تستهلك مئات الميغابايتات من الذاكرة كخدمات دائمة).

**•** **العواقب**: صفر استهلاك RAM عند الخمول، ملفات قابلة للنقل والنسخ الاحتياطي بسهولة تامة، وأداء استعلام متجهي فائق.

### ADR-004: بوابة مخاطر نقية Fail-Closed وعزل واجهة التحكم الخارجي (FR-703)

**•** **السياق**: ربط النظام ببوتات خارجية أو وكلاء ذكاء اصطناعي يفتح خطر Prompt Injection أو الأخطاء الكارثية.

**•** **[القرار ([قرار])**: جعل evaluate_risk_gate دالة نقية حتمية تمر بها جميع النوايا بلا استثناء وتفشل نحو الإغلاق (Fail-Closed)، وحصر واجهة التحكم الخارجية في أفعال الإيقاف والإغلاق والاستعلام فقط مع جعل حدود المخاطر للقراءة فقط.

**•** **البدائل المرفوضة**: السماح لواجهة التحكم الخارجية بتعديل حدود المخاطر أو إرسال أوامر تداول حرة.

**•** **العواقب**: حتى في حال اختراق وكيل الـ AI الخارجي بالكامل، فإن أقصى ما يمكنه فعله هو إيقاف التداول أو إغلاق المراكز المفتوحة (Flatten).
